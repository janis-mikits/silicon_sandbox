# Development readiness audit for the first playable professor milestone

**Status:** First-playable preimplementation design audit, updated 30 September 2026. The canonical `docs/` files settle the foundation and documented first-playable acceptance behaviors, including selected-region boundary extraction; this file tracks deferred questions and implementation/acceptance gates. This is readiness to **start** implementation, not a claim that coding will reveal no further ambiguity. No game code or benchmark result is claimed here.

## Review rule

An item is **foundation** when choosing it late could require replacing core data structures or the engine. **Before feature** means decide it before implementing the affected first-playable behavior, but other work can proceed. **Guard now** means preserve an existing later-game constraint in the first-playable design while leaving its detailed feature for later. **Defer** means it need not shape the first playable. These are planning classifications, not new game requirements or approvals of a proposed rule. Reclassify after investigation if evidence warrants it.

The first playable is ready for implementation when its required behaviors have testable expected outcomes, foundation choices have been made, every open item that affects an imminent feature has a decision or an explicit limited scope, and the implementation plan does not contradict later-game constraints. “Ready” does not mean every later feature is specified or that bugs are impossible.

## First-playable acceptance coverage

The [delivery specification](docs/delivery-and-acceptance.md) requires a flat 3D world, single-bit circuit construction, four-state event-driven behavior including offscreen simulation, signal/connection inspection, packaging of a stateful circuit into two independent instances, save/reopen of design with ordinary simulation restarted, and the [performance target](docs/performance-and-platforms.md). The [accepted first-playable correctness matrix](docs/delivery-and-acceptance.md#first-playable-internal-correctness-matrix) now supplies concrete expected results; execute it during development. Cross-check [digital simulation](docs/digital-simulation.md), [circuit time](docs/circuit-time-and-clock.md), [physical connections](docs/physical-connections.md), [modules](docs/modules-and-packaging.md), and [saving](docs/saving-and-recovery.md).

These are all five caution bullets in [Appendix B](docs/open-decisions-and-cautions.md#technical-interpretation-cautions); they are constraints on interpretation rather than unanswered feature requests.

| TC-02 | Treat equal-strength resolution, strict width refusal, MUX merge, SR invalid state, counter overflow, pulse queue, and missing-module placeholder as explicit game policies unless focused comparisons show IEEE/VCS equivalence. |
| TC-03 | Verify the applicable IEEE revision and VCS options; “latest SystemVerilog” does not imply all constructs or future revisions. |

## Additional inline open points and later-game constraints

- [Components](docs/components-and-rtl-timing.md): the SR flip-flop's S/R=X/Z behavior and Constant Logic Source initial Off default are [decided](docs/components-and-rtl-timing.md), and [positive-edge detection](docs/circuit-time-and-clock.md#four-state-positive-edge-detection) is shared across rising-edge components. Other components' unknown-data/control truth tables, independent Clock Source phase/range/world-clock relation, and LED X/Z treatment remain open. Decide only when the affected item is implemented, and never substitute a two-state fallback silently.
- [Modules](docs/modules-and-packaging.md): preserve exact spatial layout, stable port mapping, nested version references, and independent instance state from the first playable even though upgrades and re-expansion can come later.
- [Education](docs/education-and-onboarding.md) and [saving](docs/saving-and-recovery.md): Freeplay availability, one-bit-first Education progression, cross-world player profile, and per-world lesson position constrain later compatibility. The lesson content itself can wait. A mode-aware component catalog and separate profile storage are possible implementation implications to review, not newly approved architecture.
- [Future tools](docs/graphics-and-future-tools.md): automatic-route endpoint/conflict/objective/preview behavior and the relative priority of deferred features remain later questions.
- [Project vision](docs/project-vision-and-world.md): world dimensions and height are provisional/configurable; [first-playable player/developer settings and save compatibility](docs/project-vision-and-world.md#definitions-and-extensibility) are settled, with later setting roles still open.

## Review sequence and decision recording

1. Examine foundation choices with evidence: engine, simulator/backend, supported first-playable behavior, world/rendering representation, and module data/instance model. Do not accept a research-backlog premise as an answer.
2. Define a concrete professor demonstration circuit and verification cases for each of the five acceptance steps, including four-state, offscreen, independent instance, and save/restart checks.
3. Resolve each “Before feature” item immediately before implementing that feature. Preserve “Guard now” constraints in interfaces and saved data; leave the detailed later feature open.
4. Record every user decision in its canonical subsystem file and update [INDEX.md](INDEX.md) if routing, dependencies, terminology, or file responsibilities change. Mark the corresponding row here as decided with a link to the canonical rule. Do not resolve an ambiguity merely by writing code.
5. Re-run a cross-file consistency and testability check before declaring the design ready for first-playable implementation.

**Current result:** The professor milestone is **ready to start implementation**: engine and backend, supported behavior and internal checks, timestamp/event rules, sparse world and renderer boundaries, authored topology and package-boundary extraction, fixed module versions and instance state, version 1 JSON records, save/recovery, interaction controls, and a reproducible benchmark protocol have canonical homes. Actual software, the saved benchmark scene, test-machine inventory, Windows/macOS builds, correctness results, and performance measurements are still implementation/acceptance work. Region dimensions, mesh methods, graph-update algorithm, and catalog asset coordinates are chosen during implementation under the fixed behavior and saved-identity rules. If coding exposes a conflict or missing first-playable behavior, settle it in the canonical spec before implementing that behavior. Later Education, harness, upgrade, NVM, persisted undo, and large-circuit numerical targets remain staged; their existing compatibility constraints are preserved. This readiness finding does not promise zero bugs or benchmark success.

## First foundation review

The engine and simulator backend are separate choices. The user accepted Unity 6.3 LTS as the starting engine and a purpose-built C# event-driven four-state simulator as the initial backend, with simulation data independent of Unity visuals. The first playable will be the first integrated engine/performance evaluation rather than a disposable prototype. This does not prove the 1,000-gate benchmark or later large-circuit responsiveness targets. A later engine change would port engine-specific work; a later C++ simulator would require a substantial simulator rewrite and retesting, even if the Unity-facing boundary preserves other game systems. [Verilator's own documentation](https://veripool.org/guide/latest/languages.html) says it is mostly a two-state simulator, so it cannot simply be assumed to supply the game's required four-state X/Z behavior. The first-playable [component scope and internal verification matrix](docs/delivery-and-acceptance.md) are now settled; broader SystemVerilog conformance still needs a defined claim and comparison setup.
