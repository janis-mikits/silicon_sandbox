# Simulation backend research

**Date:** 29 September 2026  
**Status:** Research for [original backlog R-02](docs/original-research-backlog.md#simulation-architecture-and-hdl-integration). The user accepted the C# runtime recommendation on 29 September 2026. The canonical decision, including the substantial cost of a later C++ port, is in [digital simulation](docs/digital-simulation.md#runtime-architecture-decision). This file retains evidence and alternatives, not a second operative specification.

## Recommendation

For SiliconSandbox's interactive game, implement a **purpose-built, event-driven, four-state simulator in C#**, with circuit topology represented as data and simulation independent of rendered objects. Use Unity for world interaction, display, UI, and builds; Unity's frame loop should request or display simulation progress, not determine which electrical events occur. Do **not** make an external HDL compiler/simulator or a C++ plug-in the primary runtime for the first playable. Reserve HDL tools for conformance comparison and possible later export or import work.

This is a project-specific engineering inference from the requirements and tool documentation, not a measured claim that C# is faster than every HDL simulator or sufficient for every future circuit size. No simulation code or benchmark has been built. The [first-playable supported component subset and correctness matrix](docs/delivery-and-acceptance.md#first-playable-internal-correctness-matrix) have since been specified; broader SystemVerilog conformance remains outside that claim. On 29 September 2026, the user clarified that smooth play with large, complex circuits is a major priority and that high *simulated* clock frequencies need not run in real time; see [performance](docs/performance-and-platforms.md#platforms-and-test-machine). This strengthens the need for profiling and later scale targets but does not by itself establish a C++ speed advantage.

## Why the game needs this boundary

The canonical spec requires a player to edit circuit topology during play, operate sources live, inspect individual nets and causes of X, pause only after a settled time slot, step an edge or cycle, resume pending events, and keep offscreen circuits running. It also requires two placed copies of a packaged circuit to have independent state, and world saves to retain design plus specified NVM while restarting ordinary transient simulation at time zero. [Digital simulation](docs/digital-simulation.md) · [Circuit time](docs/circuit-time-and-clock.md) · [Modules](docs/modules-and-packaging.md) · [Saving](docs/saving-and-recovery.md)

A graph or netlist is useful **regardless of backend**: it represents nets, drivers, component ports, hierarchy, and dependencies without relying on one Unity object per electrical primitive. On a source change, an event scheduler can update affected logic; a world-clock edge does not require reevaluating every block. Render chunks may be culled or rebuilt independently, while the full circuit remains active. This follows the existing event/offscreen requirements; it is not a new rendering decision. [Circuit time](docs/circuit-time-and-clock.md) · [Original research question](docs/original-research-backlog.md#simulation-architecture-and-hdl-integration)

The world file cannot be only a SystemVerilog file: the canonical save must preserve exact 3D layout, connector topology, player position, inventory, module version identities, port mappings, tags, undo history, and NVM. HDL could at most be a generated functional representation or interchange artifact alongside that game data. [Saving](docs/saving-and-recovery.md) · [Modules](docs/modules-and-packaging.md)

## Candidate approaches

| Approach | What official documentation establishes | Fit for SiliconSandbox |
| --- | --- | --- |
| **Purpose-built C# event simulator** | Unity's C# environment can host game code; this is a design option, not a third-party simulator claim. | Best fit for live edits, exact game-defined X/Z rules, cause diagnostics, safe pause, independent module state, and direct connection to the save model. The team must implement and test the supported logic/event subset carefully. Performance remains unproven until the milestone benchmark. |
| **Verilator as primary runtime** | Verilator compiles an HDL design into C++/SystemC and then a simulation executable; its guide says it is mostly **two-state**, with X values mapped according to options. [Overview](https://veripool.org/guide/latest/overview.html) · [Input languages](https://veripool.org/guide/latest/languages.html) | Poor primary match for the required X/Z behavior. Rebuilding a compiled model after player edits would also add a compile step, and generated-model integration would need custom plumbing. This conclusion is an inference from its documented flow and semantics, not a timing benchmark. |
| **Icarus Verilog/VVP as primary runtime** | Icarus compiles source into a VVP simulation file, then VVP runs it. VPI permits C integration. Icarus exposes 2023 language selection but documents ongoing SystemVerilog support. Its embeddable VVP library says it was **not designed** for that use and normally expects one simulation run per loaded library. [Getting started](https://steveicarus.github.io/iverilog/usage/getting_started.html) · [Flags](https://steveicarus.github.io/iverilog/usage/command_line_flags.html) · [VPI](https://steveicarus.github.io/iverilog/usage/vpi.html) · [Library limits](https://steveicarus.github.io/iverilog/usage/vvp_library.html) | More plausible as a four-state *comparison tool* than Verilator. Making it the live game runtime would still require compilation after structural changes, an integration/control layer for stepping and inspection, and Windows/macOS packaging. The documented library limits create additional lifecycle risk. Specific behavior must be checked against the game's rules. |
| **Custom C++ native plug-in** | Unity supports desktop native plug-ins, with separate macOS and Windows binaries. [Unity desktop plug-ins](https://docs.unity3d.com/6000.0/Documentation/Manual/plug-ins-for-desktop.html) | Feasible later if profiling proves a C# hot path inadequate. Starting there adds native build, cross-platform binary, memory, and C#/C++ boundary work before a bottleneck is demonstrated. It would still require writing the same four-state/game-policy simulator. |

VCS remains the [specified comparison reference](docs/digital-simulation.md#reference-and-scope), not a game dependency or bundled runtime. Icarus can add a freely available comparison for cases it supports, but its support for a `-g2023` flag does not establish complete IEEE 1800-2023 conformance. Preserve explicit game policies where they differ from a reference simulator. [Icarus language flags](https://steveicarus.github.io/iverilog/usage/command_line_flags.html) · [Technical cautions](docs/open-decisions-and-cautions.md)

## What the recommendation commits to if accepted

- A circuit graph/netlist derived from the editable world and module definitions, with independent runtime state for every placed instance. The world and package saves retain original geometry and mappings as already required.
- Four-state values and driver resolution, event ordering/delta settling, scheduled clock edges, pause/step/resume, convergence handling, and offscreen operation must all be represented explicitly. The design should expose values and causes needed by Inspect; renderer visibility cannot decide simulation membership.
- Structural edits update the relevant graph/topology at the safe edit boundary. The exact incremental update algorithm is an implementation choice, not settled by this research.
- Verification should use deterministic truth-table and event-sequence tests, module-instance independence checks, save/reset checks, and focused comparison with the specified VCS configuration when available. Do not claim full SystemVerilog language support for a component-level game simulator.
- Profile the actual first playable before deciding whether native acceleration is needed. The user has chosen not to build a separate disposable engine/performance prototype. [Benchmark](docs/performance-and-platforms.md#benchmark)

## Remaining questions and limits

1. The [first-playable component subset and internal correctness matrix](docs/delivery-and-acceptance.md#first-playable-internal-correctness-matrix), [four-state game policies](docs/digital-simulation.md), and [supported scheduler contract](docs/circuit-time-and-clock.md#first-playable-scheduler-contract) now settle what to build and test for that milestone. Broader IEEE/VCS conformance still needs an explicit construct claim, tool configuration, and additional comparisons before that claim is made.
2. First-playable simulation precision, clock range, checked timestamp representation, and no-drift world-clock scheduling are settled in [circuit time](docs/circuit-time-and-clock.md#first-playable-scheduler-contract). Phase/range for later independent Clock Source components remains before those features.
3. The [module representation](docs/modules-and-packaging.md#canonical-design-and-runtime-representation) and [version 1 data schema](docs/first-playable-data-schema.md) now settle authored versus derived data, exact identities/references, and independent instance state. Implement and test them; the code's graph indexes and data structures are measured implementation choices.
4. Benchmark actual frame and simulation rates at the professor milestone. No source reviewed proves the 1,000-equivalent-gate target for either C# or an external tool. [Performance](docs/performance-and-platforms.md#benchmark)
5. Set later large-circuit reference workloads and responsiveness/throughput targets before claiming the architecture scales to the full game. A high modeled frequency is a time-scale setting, while processing every resulting transition over a long simulated interval can still require substantial computation. [Performance clarification](docs/performance-and-platforms.md#platforms-and-test-machine) · [Circuit time](docs/circuit-time-and-clock.md#clock-and-event-model)

**Decision recorded:** The user accepted the C# event-simulator direction and the separation from Unity visuals. A later C++ move would require rewriting and retesting the simulator core; the separation protects other game systems but is not cost-free. It remains possible to compare HDL tools during development without making them the shipped runtime.
