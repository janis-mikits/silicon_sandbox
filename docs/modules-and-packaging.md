## Definition and instance

Packaging copies a selected world circuit into a reusable module definition and leaves the original circuit in place. The definition is not connected to the source circuit after packaging, so editing that circuit does not revise the module. The original may be destroyed without destroying the definition. A placed module is a separate instance of the saved design. This mirrors the distinction between a SystemVerilog module definition and its instantiated copies and supports teaching abstraction: modules may contain other modules, so players can build increasingly complex systems. Direct or indirect recursive containment is invalid. A parent definition records exact child-module versions, so a later child update does not alter the parent silently.

Packaging follows the [all-or-nothing operation rule](circuit-time-and-clock.md#safe-pause-and-editing): the fixed definition and its library/inventory reference become available together only after validation succeeds; a rejected package leaves both absent and the source design unchanged.

## Canonical design and runtime representation

**Decision, 29 September 2026:** Treat an editable world circuit as an authored design blueprint containing both its electrical connections and exact three-dimensional layout. Packaging copies the selected design into a fixed module-version blueprint, independent of the source circuit. A placed module refers to that exact version but has its own mutable simulation state; two instances never share current signals, registers, volatile memory, pending events, or other runtime state. The simulator derives a working connection graph/netlist from the authored world and referenced module versions. That graph is rebuildable working data, not a second authoritative definition or a substitute for the retained 3D design. This representation supports the live internal viewer and physical re-expansion as specified below. See [the accepted-model research record](../module-data-model-proposal.md) for rationale.

World saves retain the authored design and exact embedded referenced module versions as specified under [library and world independence](#library-and-world-independence), the accepted [first-playable save container](saving-and-recovery.md#first-playable-world-save-container), and its [version 1 JSON record contract](first-playable-data-schema.md). The authored connector and join structure follows the [topology representation](physical-connections.md#authored-topology-representation). The graph may be rebuilt on load; ordinary instance runtime state restarts under the save rules, while per-instance nonvolatile memory follows its persistence exception. Exact C# classes and the measured graph-update algorithm remain implementation choices. The accepted identity semantics are specified below. The model must preserve the existing port, nested-version, missing-module, and save-compatibility rules; this decision does not settle unrelated open design points.

## Persistent identity model

**Decision, 30 September 2026:** Give worlds, module families and fixed versions, authored objects, connectors and targetable connection parts, ports, and placed instances persistent opaque identities. An authored part's identity is scoped to its owning world design or fixed module-version design. A particular internal part in a live or saved nested instance is identified by its exact module version, its local authored identity, and the chain of containing instance identities; this distinguishes two placements of the same version without duplicating its immutable design. A port's identity and its bit index identify a mapped bit when wider ports are implemented. Names, positions, orientations, Unity runtime object IDs, and derived graph indexes are not substitutes for these persistent identities.

New independent copies and placements receive new instance identities. Moving or rotating an existing object or instance retains its identity. Packaging creates a new fixed module-version identity and independent authored snapshot while leaving the source world's objects and identities in place. Repackaging creates another version; existing placements remain pinned to their exact versions. The derived simulator and renderer may map persistent identities to compact runtime indexes for speed, but the indexes are rebuildable and cannot silently become saved identity. Preserve identity references through save/reopen and use them to associate instance-specific state and selection with the right design object.

**ID generation decision, 30 September 2026:** Generate new persistent identities as random 128-bit UUID version 4 values under [RFC 9562](https://www.rfc-editor.org/rfc/rfc9562.html). Use this for world, module-family/version, authored-part, connector, port, and instance identities. Identify a bit of a wider port by its port ID plus bit index rather than assigning a separate UUID to every bit. Validate ID uniqueness and references when generating and loading data; a duplicate or conflicting identity must not silently overwrite an object or resolve to the wrong definition. UUIDs identify durable design entities, not individual simulation events. When a break leaves two connector pieces, follow the [connector split identity rule](physical-connections.md#authored-topology-representation). The [version 1 JSON schema](first-playable-data-schema.md) defines first-playable references; identity handling for other later structural replacements remains to be specified before those operations are implemented.

**UUID text decision, 30 September 2026:** Write UUIDs in lowercase, hyphenated `8-4-4-4-12` form, for example `123e4567-e89b-42d3-a456-426614174000`. When loading, validate each UUID, accept either letter case in that form, and compare parsed UUID values rather than raw text. Differently cased strings for the same UUID do not represent distinct identities; duplicate-ID and reference checks use the parsed value. Re-saved files use the lowercase form.

## Packaging region and ports

The existing two-corner selection chooses a rectangular three-dimensional region. The packaging preview identifies boundary-crossing connectors, qualifying Net Links, and exposed component pins as candidate ports. Each port records a unique case-sensitive name, direction (input, output, or inout), width 1–128, packed-vector order, exterior face and quadrant/position, stable internal identifier, and exact internal net/bit mapping. Input takes an external driver inward; output drives outward; inout can be driven from either side. All three simulate in the core, though education can introduce inout later. Multiple separate exterior ports may map to one internal net; show that relationship and resolve any driver conflict normally. Direction inference is an editable starting heuristic: internal receivers with no internal driver suggest input; internal drivers suggest output; deliberate bidirectional or tri-state paths suggest inout. The player can correct the name and inferred direction and move the exterior face before packaging, but cannot remove a connected candidate or remap it to a different internal endpoint.

The module can expose ports on all six sides, with at most four pins per block face. The previously inconsistent module-length example is corrected: for separate input and output faces, a 12-input/8-output interface requires ceil(max(12,8)/4) = 3 block lengths, counting ports rather than individual bus bits. The final exterior size and pin layout must fit every required physical position independently of the captured circuit's internal bounds. By default, a package with at most four pins on each used face occupies one exterior block even if the selected circuit spans multiple cells. A connector that merely passes through the selected region without connecting to anything inside is ignored. A connector that connects to an object inside qualifies as a port candidate even if nothing is attached to its outside end; packaging cares about the selected circuit’s internal connection. An internal Net Link connected to the selected design is handled under the same boundary/port mapping rules.

**First-playable boundary extraction rule, 30 September 2026:** The preview selects whole components, blocks, and placed modules whose complete occupied footprints lie inside the inclusive two-corner region. If a placed object's footprint intersects the region but is not wholly inside, reject the package preview until the player changes the selection; never capture a partial component or module. For each selected circuit's one-bit connector, copy only route nodes and spans inside the region and terminate every crossing at the exact boundary face. Preserve the electrical joins among the copied inside pieces, remapping their IDs into the fixed blueprint. A route that exits and later re-enters the region becomes separate inside pieces unless an inside path or explicit inside junction also connects them. Do not infer their connection through omitted outside geometry. Show a port candidate for every boundary crossing belonging to an inside-connected circuit; its mapping names the exact copied internal endpoint or net. Every connected candidate remains an exterior port, even when two candidates map to the same internal net; the preview shows the exposed mappings before confirmation. An exposed outward-facing pin on the boundary may map directly to a port. Pure pass-through routes with no selected internal connection remain excluded as above. Packaging leaves every source-world object and connection unchanged; an invalid cut, ambiguous mapping, occupied exterior port position, or unresolved preview choice prevents publication under the [all-or-nothing rule](circuit-time-and-clock.md#safe-pause-and-editing). This rule fixes topology and validation, while the UI may choose its preview layout.

**Boundary-only port clarification, 6 October 2026:** The user confirmed that padding a selection does not automatically promote an unwired pin inside the region into an exterior port. To expose that pin, route a connector to the selected boundary or select a region where the outward-facing pin itself lies on the boundary. For example, an unwired Q_bar pin on an SR block inside a larger 3 × 2 selection is not an exterior candidate unless it reaches the boundary, while Q_bar is included when the SR cell itself is selected. This boundary rule and the requirement to retain every *detected* connected candidate apply together.

## What is captured

A definition stores layout, components, internal connectors and bit mappings, nested module versions, settings, explicit initialization and reset rules, and ROM/design images. It captures the design, not the running circuit’s current values. A counter that reads 0110 at package time does not make every future copy start at 0110. Runtime register contents, volatile RAM, current transient signals, pending events, clock phase, and simulation time are not copied into the definition. New instances start from defined initialization/reset values or X. Each instance has independent internal nets, Net Links, memory, register state, event state, and hierarchical identity. Its instance name is unique within its containing world or module. Copying an instance creates a fresh instance; removing an instance discards its internal runtime state; rotation of the same instance preserves it. A live internal viewer shows the selected placed instance’s actual current state and permits navigation into nested child instances without modifying it.

## Placement

A multi-block module occupies its entire required footprint. The preview shows orientation, port layout, and obstructed cells. Every target cell must be empty; otherwise placement fails atomically and uses the same brief red flash and quiet invalid-action sound as other invalid placements. The module never overwrites or partially overlaps existing blocks. The rotation rule from [Section 3](physical-connections.md) applies to already placed modules with an additional complete-footprint fit check.

## Creating versions and upgrading

There can be more than two versions. The only way to add a version is to make or edit an ordinary circuit and package it again, selecting “new version of existing module.” Repackaging the old source or a re-expanded copy are both valid workflows. An edit to a source circuit alone creates no module version because the packaged definition has no live source link. Existing placed instances remain pinned to their exact versions; new placements use the newest version by default. The player deliberately upgrades compatible instances individually or in a group. This is important because a faulty design can be corrected once and used to upgrade many instances without replacing every block by hand; pinning prevents an update from silently altering working worlds.

In-place version upgrade requires matching case-sensitive port names, directions, widths, packed-vector ordering, exterior pin coordinates/faces/quadrants, and module footprint. Internal circuitry may differ. An incompatible interface or footprint cannot be migrated in place. A changed-interface or changed-footprint design can be packaged as a separate module. Open: whether an incompatible revision may also be stored under the same family for new placements. The confirmed restriction is that it cannot be used for an incompatible in-place upgrade; family membership alone does not establish upgrade compatibility. Upgrade auto-pauses and settles safely. The upgraded instance starts fresh from the selected version’s initialization; old registers, volatile memory, pending events, and nonvolatile memory do not transfer. Warn clearly before an upgrade would replace existing nonvolatile contents. A later explicit memory-migration tool remains possible, but is not part of the accepted core behavior.

## Library and world independence

A module version may not be deleted from the global library while indexed saved worlds use it; it may be archived out of ordinary inventory while retained for those worlds. A world save embeds every exact referenced module version and nested dependency, with module family ID, module version ID, embedded-definition integrity hash, and instance ID, so a missing global library entry can be supplied by the saved copy. Loading should verify the exact definition, avoid silent substitution of a newer version, and offer to restore a missing global entry. If both global and embedded definitions are missing or damaged, the world still loads with a visibly marked placeholder retaining footprint, pins, and connections. Its output and inout ports drive X; the player can relink an exact compatible definition. A missing module is never silently deleted.

## Physical re expansion final rule

After a temporary decision to remove physical re-expansion, the user restored it because a destroyed source circuit should be recoverable for editing and repackaging. “Expand Module” places a new editable copy of the saved circuit design and layout in the world. It does not replace a placed instance, update the library definition, or copy a live instance’s current state. The player targets the cell intended to be the bottom-right corner of the circuit. A ghost shows the complete saved footprint and orientation. All required cells must be empty; if not, nothing is placed and the usual invalid-action effects occur. The expanded design starts from defined initial conditions. The definition must therefore retain its original spatial layout, not only its functional netlist. The new editable copy can be changed and packaged as a new version. The separate live internal viewer remains available for inspection. The exact view-dependent 3D meaning of “bottom-right” and the command’s entry point still need a UI convention.

## Selection and package configuration

Target a block, connector, component, or existing module and press R for the first corner, then T on a second object for the opposite corner. Show the rectangular bounding box while selecting. R and T may revise either corner before Enter/Return confirms it. For corners (0,0,0) and (5,5,5), the eight corners are (0,0,0), (5,0,0), (0,5,0), (5,5,0), (0,0,5), (5,0,5), (0,5,5), and (5,5,5).

**Professor walkthrough presentation correction, 6 October 2026:** Draw the selected region as a roughly 50%-transparent outline that leaves the enclosed circuit visible. Escape before confirmation clears the corners and outline. The package configuration controls and text need a substantially larger, readable layout; at 1080p target roughly triple the provisional text size, using scrolling when the desired physical panel size cannot fit on screen. Connected ports are retained under the rule above. The approved [pre-release version 1 correction](first-playable-data-schema.md#module-versions-and-instances) stores the compact exterior separately from the captured internal layout.

The package configuration page has seven areas in three rows: a top preview that rotates by click-and-drag, then two rows of three lists corresponding to the six exterior faces. Move ports between face lists, edit their names and inferred directions while preserving their exact internal mappings, and choose module dimensions. An exposed pin qualifies when it lies on the selection boundary and faces outward so a connector outside could reach it. The original input/output tests also include a boundary-crossing wire or harness attached to an internal input/output, and an internal Net Link attached to such a pin. Apply the confirmed pass-through exclusion and editable input/output/inout inference above to these candidates.

By default place inputs on one side and outputs on the opposite side, like faces 1 and 6 of a die, with the default one-block-high length calculated using ceiling(max(input ports, output ports)/4). A single block supports at most 24 pins across six faces. Larger interfaces require a larger object. One 128-bit bus pin still takes one quadrant. Open: default arrangement of inout ports and a zero-port minimum footprint.

The module must remain a rectangular prism. With 32 input ports on one face, the player can choose a face 1 by 8, 2 by 4, 4 by 2, or 8 by 1 blocks. A 3 by 3 face supplies 36 positions, leaving one block face unused. Layout choices must have enough positions for every port.

The Confirm button is at the bottom of the configuration page. Confirmation adds the reusable module object to the inventory and global module library, accessible in every world. Players can place unlimited instances, subject to available world space and performance. Packaging does not remove the original build.

## Educational fidelity and optimization

Do not automatically redesign a player-made module into a logically simplified or structurally different circuit that hides the design the player actually built. The original aim is to let players compare efficient and inefficient designs. General simulation and storage optimization is allowed while preserving modeled behavior and the captured circuit shown in the live viewer. With zero physical delay, simulator CPU time cannot stand in for real circuit speed. Open: the exact invariant list for intermediate signals, gate counts, event ordering, and optimization boundaries.
