## Platforms and test machine

Windows and macOS are target operating systems. The user wants performance on a PC representative of an ordinary Steam user, acknowledging that the survey changes over time. The accepted platform answer applied to the first playable version as well as the public release. **First-playable measurement procedure, 30 September 2026:** Choose one available Windows machine and one available Mac before acceptance measurement, record CPU/GPU/RAM/OS, freeze those machines and settings for that milestone, and rerun the same saved scene on both. Document whether the Windows machine is representative of the then-current ordinary Steam PC; if that has not been verified, report it as an unverified representativeness claim rather than inventing a minimum specification. Machine acquisition and measurement are acceptance-time work, not prerequisites to writing the first playable. The chat cited August 2026 examples of 1080p, 16 GB RAM, and RTX 3060; those historical claims are not a verified current survey snapshot or a chosen minimum specification.

**Clarification, 29 September 2026:** Smooth, responsive play with large, complex player circuits is a major long-term priority. High simulated clock frequencies should be representable, but the user does not require those circuits to execute at that frequency in real time. The game must continue to distinguish simulated circuit time from achieved simulation throughput, as specified below and in [circuit time](circuit-time-and-clock.md#clock-and-event-model). No numerical large-circuit size, frame-rate threshold beyond the existing first-playable benchmark, or high-frequency range was selected by this clarification; these remain to be defined and measured in later acceptance work.

## Benchmark

For the first playable milestone, the target is at least 60 rendered frames per second at 1080p on the chosen standard preset for player circuits containing 1,000 equivalent one-bit gate operations or fewer. Measure the boundary case with a saved reference scene containing 1,000 equivalent one-bit gate operations. Count gates inside module instances; a 128-bit bitwise AND represents 128 one-bit gate operations, not one. Every benchmark result must record the test machine’s operating system, CPU, GPU, and memory, plus the display resolution and graphics preset. Also record connector-segment count, harness widths, module-instance count, register count, visible objects, and activity. Test a mostly idle and a frequently switching circuit, stationary and flying camera, ordinary editing, and circuits both visible and out of view. Offscreen simulation must produce the same electrical results; hidden geometry may be culled. Record average frame rate and stutters, not only a single peak number.

**Professor benchmark scene choice, 30 September 2026:** Make the saved 1,000-equivalent-one-bit-gate reference world a mixed scene containing individual gates, visible connectors, and packaged module instances. Use that same reference world for mostly idle and frequently switching activity and for stationary and flying camera conditions. The protocol below fixes the gate distribution, activity, preset, and reporting criterion. Its exact cell layout, camera route, actual machines, and measured results are completed during benchmark construction and measurement; this choice does not assert that the scene already meets the target.

**First-playable reference protocol, 30 September 2026:** The saved benchmark world contains exactly 1,000 one-bit AND operations: 500 individually placed AND components and ten instances of one immutable module version containing 50 one-bit AND components each. The module instances count as 500 additional operations. Include the connectors and sources needed to drive and inspect them; report their actual counts and keep the saved file fixed across test machines and renderer comparisons. A separate professor demonstration world tests the SR flip-flop and stateful packaging behavior. In the idle run, stop the world clock after the circuit settles. In the active run, drive representative gate inputs so the 10 Hz world clock causes the gates and visible connectors to change; report the achieved clock-edge rate rather than dropping edges. The benchmark scene's exact cell layout and camera route are fixed when the reference world is authored, then checked into the project with a documented hash before comparison. This is a scene-construction task during development, not an unresolved game mechanic.

Use the game's default **Standard** graphics preset at 1920 × 1080, 100 percent render scale, with frame-rate cap and VSync disabled for measurement. Record all graphics settings and engine quality options in the benchmark report so the same preset can be recreated. After a 10-second warm-up, measure 60 seconds for each of four cases: idle/stationary, active/stationary, idle/flying, and active/flying. Replay the same recorded camera path for flying runs on both platforms. The first-playable target is average rendered FPS at least 60 in each case; also report median, 95th- and 99th-percentile frame times and the maximum frame time. Treat a 99th-percentile frame time above 33.3 ms as a visible-stutter finding requiring investigation even if average FPS passes; do not hide it behind the average. Repeat ordinary place, break, and undo at the same set of locations, including a render-region boundary; each scripted operation after warm-up should meet the provisional 100 ms response target, and the report includes every latency. Check manual save within 2 seconds and load within 5 seconds with the same world. If a provisional response or stutter criterion proves unrealistic, revise it explicitly with measured evidence before claiming acceptance; never quietly redefine the benchmark after seeing results.

**First-playable Standard preset, 5 October 2026:** The project's Unity `Standard` quality level starts from the Editor's built-in Medium values: one pixel light, hard shadows at the lowest shadow-resolution tier with 20-unit shadow distance, no MSAA, full texture resolution, anisotropic textures enabled, and LOD bias 0.7. Standalone builds and the Editor select it by default. VSync is off, the frame cap is disabled for benchmark measurement, and the built-in renderer uses 100 percent render scale. Record the complete quality options and actual resolution in every result; this fixes the comparison setting but does not imply a performance pass.

In active cases, the requested 10 Hz world clock should achieve its ten complete cycles per real second over the measured interval while every required electrical edge is processed; report achieved cycles/second and simulation CPU time separately from FPS. A shortfall is a benchmark failure to investigate, not a reason to skip transitions or silently lower the requested rate. This first-playable throughput check does not promise real-time operation for later larger circuits or a simulated 1 GHz clock.

Track three different things: rendered frame rate; requested versus achieved simulation rate in world-clock edges per real second; and the player circuit’s structural/logical metrics, such as equivalent gates, registers, logic depth, and cycles per result. Never skip clock edges silently to meet requested speed. Simulation CPU time measures engine workload, not the circuit’s real physical speed. The agreed first-pass response targets on the specified 1,000-gate benchmark are ordinary place/break/undo within 100 ms, manual save within 2 seconds, and load within 5 seconds. These numbers remain provisional until measured on the selected Windows PC and Mac test machines; large paste/package actions need separately defined budgets when those features are implemented. The Standard preset's concrete Unity option values and the camera/layout artifact will be frozen during reference-scene construction before measurement under the protocol above.

## Rendering optimization checks

**Decision, 29 September 2026:** Evaluate rendering techniques against the same saved scene and settings on each test machine. Record frame-time distribution and visible stutters, main-thread rendering work, GPU time, region rebuild/edit latency, memory, and simulator throughput separately, in addition to the [benchmark fields](#benchmark). Compare relevant scene shapes: sparse scattered components, dense opaque blocks, many exposed connectors, repeated modules, frequently switching signals, and edits at render-region boundaries. Include stationary and flying camera cases and both visible and out-of-view circuits. The first-playable benchmark remains the current numerical target; large-circuit thresholds are still open.

Optimization comparisons must also verify the [rendering and update invariants](graphics-and-future-tools.md#rendering-and-update-invariants) and [renderer boundary contract](graphics-and-future-tools.md#renderer-boundary-contract): exposed faces appear correctly after placement, removal, rotation, load, undo, and redo; there are no boundary gaps or stale asynchronous results; thin connectors, pins, channels, crossings, and floor cells remain targetable; visual state reflects settled four-state values after returning from out of view; and culling does not change offscreen electrical results or skip clock events. An optimization that improves FPS while failing those checks is not acceptable. Test the supported Windows and macOS paths before requiring a hardware-specific rendering method.
