## Recommended first cloud trial, pending user authorization

[Unity Build Automation](https://docs.unity.com/en-us/build-automation) is an official Unity cloud CI service that supports Git repositories, macOS and Windows desktop builds, and [Edit Mode and Play Mode test execution with failure gating](https://docs.unity.com/en-us/build-automation/reference/unit-tests). Unity lists [6000.3 LTS as supported](https://docs.unity.com/en-us/build-automation/reference/supported-unity-versions); the Dashboard must still confirm the exact project patch `6000.3.24f1` is available. This path avoids attaching a personal machine to the public repository. It is a **proposed additional external service**, not authorized or connected by this file. The user must first confirm service use and handle sign-in, repository authorization, and any plan or billing decision personally. Do not put tokens in chat, source, CI logs, or build artifacts.

Once authorized, make one **manual trial** before enabling automatic builds:

1. In the Unity Dashboard, create/select a DevOps project and connect only `janis-mikits/silicon_sandbox` as the Git source. Unity's [source-control instructions](https://docs.unity.com/en-us/build-automation/get-started-with-build-automation/connect-your-version-control-system) describe a fine-grained GitHub token restricted to this one repository with `Contents: read-only` for a manual build. The user creates and enters that token directly in the Dashboard. Webhook write permission is needed only if auto-build is later enabled; leave it off for the trial.
2. Create a **macOS desktop** target on branch `main`. Set the project subfolder path to `UnityProject`, because `Assets` and `ProjectSettings` live there. Select or auto-detect exact Unity `6000.3.24f1` from the committed `UnityProject/ProjectSettings/ProjectVersion.txt`. Choose the Mac builder and matching Editor architecture in [Basic Info](https://docs.unity.com/en-us/build-automation/basic-build-configuration/overview). Keep auto-build **off** for the first run.
3. In Advanced Settings → Tests, select **Run my project's unit tests**, **Run EditMode tests**, **Run PlayMode tests**, and **Mark build as failed if any test fails**. Run one build at the current reviewed commit. The local baseline is **192 Edit Mode and 17 Play Mode passed**, plus the native Mac build and player smoke. Cloud test counts must be checked in the downloaded reports rather than assumed from a green build icon.
4. Review the exact commit, Editor version, package resolution, test counts, skipped/inconclusive/failures, and build log in [Build History](https://docs.unity.com/en-us/build-automation/check-build-results/overview). Save the run ID, target, commit, counts, and report links in a repository verification note. If the cloud environment cannot run a graphics-dependent Play Mode test, report that failure and fix the runner or test environment; do not count a skipped suite as a pass.
5. If that trial succeeds and the user approves further service use, add a Windows desktop target with the same subfolder, branch, Editor pin, and failure-gated Edit/Play tests. Windows **build/test** evidence from that target would improve platform coverage; it would not replace a native Windows player walkthrough or Windows performance measurement. The user has temporarily waived the latter.

Unity's [free-plan documentation](https://docs.unity.com/en-us/devops/pricing/free-plan) says usage limits apply and excess usage can lock the DevOps project until a plan upgrade. Check current allowance in the Dashboard before running either target. No billing or paid upgrade is implied or authorized here.

## What a cloud trial would and would not prove

An actual Unity Build Automation run can prove that its configured Editor imported this commit, ran the selected Edit/Play suites, and produced its target build. It does **not** automatically execute this repository's `scripts/verify-unity.sh` or `scripts/verify-unity.ps1`, nor their separate built-player startup, V1 save/reopen, and exit-autosave smoke steps. The Play Mode suite does exercise those persistence rules in the Editor, but that is narrower than built-player parity. After the first cloud run reveals its artifact layout, add and run a reviewed post-build player smoke step or provision safe licensed GitHub runners before claiming that cloud CI runs the *same* full local gate. The current GitHub Actions workflow remains manual-dispatch with no executed jobs until runners are configured; the older queued run above is not a pass. A Unity Build Automation success must be labeled as Unity Build Automation evidence, not GitHub Actions evidence.

The separate [1080p graphical Mac benchmark](benchmark-reference-progress.md) is a local measured acceptance run. Cloud build/test machines, especially those without a suitable GPU/display, are not substitutes for its graphical FPS and input-response results. The [manual professor walkthrough](professor-manual-walkthrough.md) is also still required for control and visual acceptance.
