# Circuit and module data model proposal

**Date:** 29 September 2026  
**Status:** Conceptual model accepted by the user on 29 September 2026 for [research item R-03](docs/original-research-backlog.md#module-representation-and-reconstruction). The canonical decision is in [modules](docs/modules-and-packaging.md#canonical-design-and-runtime-representation). This file retains the rationale, proposed data layers, and implementation questions; it is not a second operative specification. [Saving](docs/saving-and-recovery.md), [physical connections](docs/physical-connections.md), and [digital simulation](docs/digital-simulation.md) also constrain the model.

## The central choice

**Accepted: one authoritative authored circuit design, with a derived simulation graph.** The authored design retains every placed object's identity and 3D layout, connector geometry and electrical joins, component configuration, port mapping, and exact nested module-version references. A graph/netlist is built from that design for efficient C# event simulation. The graph is an internal working form or rebuildable cache, not a replacement for the authored design. Saving only the graph would lose the exact layout required for the live viewer and physical re-expansion. Saving unrelated full copies of both the authored topology and a second authoritative graph would risk disagreement after edits. The latter rationale is an engineering inference, consistent with Unity's advice to avoid serializing redundant cached data. [Unity serialization best practices](https://docs.unity3d.com/6000.0/Documentation/Manual/script-serialization-best-practices.html)

## Proposed data layers

| Layer | Contains | Relationship to other layers |
| --- | --- | --- |
| **World authored design** | Placed objects and connectors, positions/orientations, explicit connections, settings, tags, and module-instance placements with stable identities. | Edited by player actions; saved under [world-save rules](docs/saving-and-recovery.md). Source circuit remains in place after packaging. |
| **Module-version design snapshot** | A copied, fixed version of the selected authored circuit, preserving internal layout/topology, component settings and initialization, exact nested child versions, port identities/bit mappings, and footprint. | A new version is created only by repackaging an ordinary circuit. Existing placed instances keep their exact version. The snapshot is independent of the source circuit. [Module rules](docs/modules-and-packaging.md#definition-and-instance) |
| **Compiled simulation graph** | Nets and individual bit nets, drivers/receivers, component dependencies, hierarchy references, and scheduling lookup data needed by the C# simulator. | Derived from world and module designs; rebuilt or updated after safe structural edits. Rendering visibility does not remove graph members. Exact cache format and incremental-update method remain implementation choices. [Simulation](docs/digital-simulation.md#runtime-architecture-decision) |
| **Instance runtime state** | Per placed instance: its internal net values, registers, volatile memory, pending events, clock phase, and hierarchical identity, recursively including nested instances. | New/copy instances get fresh state from the version's initialization rules. Two instances may share a read-only version design but never share mutable runtime state. Ordinary transient state is not restored on world reopen. [Module capture](docs/modules-and-packaging.md#what-is-captured) |
| **Saved persistent instance data** | Per-instance runtime-writable NVM contents, including NVM inside nested module instances, alongside world design and embedded exact module-version definitions. | Saved and restored by the [NVM exception](docs/saving-and-recovery.md#nonvolatile-exception); not confused with ordinary transient state. Stable identity is needed to attach each NVM image to the correct instance after reopening. |
| **Unity presentation** | Visible meshes/GameObjects, hit targets, highlights, Inspect panels, and editor UI. | Reads or requests design/state information. It is not the authoritative record of topology, module contents, or simulation membership. Offscreen circuits still simulate. [Physical connections](docs/physical-connections.md) · [Circuit time](docs/circuit-time-and-clock.md) |

This is a conceptual split, not a prescribed set of classes or files. A physical world save may package several layers together as the existing save rules require.

## Key operations under this proposal

1. **Package:** At the confirmed safe boundary, copy the selected authored circuit into a new module-version design snapshot; record exact port-to-internal-bit mapping and nested version references. Do not copy the source circuit's running values, events, or transient memory. Keep the source circuit in the world. [Packaging](docs/modules-and-packaging.md#what-is-captured)
2. **Place or copy:** Store an instance's exact version identity, placement, orientation, name, and stable instance identity. Initialize a new, independent runtime state from that version's rules. Sharing the immutable version data for storage efficiency is acceptable; sharing mutable state is not. [Instances](docs/modules-and-packaging.md#definition-and-instance)
3. **Inspect a placed module:** Present the version's saved 3D layout with *that instance's* current internal values, including nested instances. Do not modify the definition when inspecting. [Live viewer](docs/modules-and-packaging.md#what-is-captured)
4. **Save/reopen:** Save authored world design, exact embedded referenced versions and integrity hashes, NVM associated with stable instance paths, and the other required world data. Reopening reconstructs the graph and ordinary runtime state from time zero, then restores NVM according to the specified persistence rule. Never silently substitute a newer module version. [Library/world independence](docs/modules-and-packaging.md#library-and-world-independence) · [Saving](docs/saving-and-recovery.md)
5. **Expand:** Make a *new editable authored circuit copy* from the saved version layout and design settings at the selected location. Do not use a live instance's current state and do not replace that instance. [Re-expansion](docs/modules-and-packaging.md#physical-re-expansion-final-rule)
6. **Upgrade:** Keep old instances pinned unless the player deliberately selects a compatible new version. Apply the specified fresh-state/NVM warning rules. [Versioning](docs/modules-and-packaging.md#creating-versions-and-upgrading)

## Why this avoids costly later changes

- **Future larger modules and nested modules:** Version snapshots retain exact child versions and spatial layouts; independent runtime state scales hierarchically without copying authored geometry into every instance.
- **Performance:** The simulator can use compact graph data and update affected events without making rendered GameObjects the unit of simulation. Graph building and change propagation still need measurement; this proposal makes no throughput promise. [Performance](docs/performance-and-platforms.md)
- **Engine/backend changes:** A versioned game-data format and behavioral tests would make migration more controlled. They would not make a later engine or C++ simulator port automatic or cheap. [Backend decision](docs/digital-simulation.md#runtime-architecture-decision)
- **Save compatibility:** Stable identities and versioned saves let a loader detect missing definitions, preserve placeholders, and migrate copies as already specified. The [UUIDv4 identity format](docs/modules-and-packaging.md#persistent-identity-model) and [first-playable ZIP/JSON container](docs/saving-and-recovery.md#first-playable-world-save-container) were selected after this proposal; the first-playable JSON records are now canonical in the [version 1 schema](docs/first-playable-data-schema.md). [Saving](docs/saving-and-recovery.md#world-and-format-operations)

## Implementation follow-through and later decisions

1. The [persistent identity model](docs/modules-and-packaging.md#persistent-identity-model), [two-piece connector split rule](docs/physical-connections.md#authored-topology-representation), and [version 1 authored JSON schema](docs/first-playable-data-schema.md) settle the first-playable IDs, route/join records, typed references, port mappings, archive entries, and loader-validation behavior. Implement them without treating this older proposal as a competing schema.
2. The [all-or-nothing structural edit and packaging rule](docs/circuit-time-and-clock.md#safe-pause-and-editing) settles rejection behavior and coherent publication. The [graph refresh rule](docs/digital-simulation.md#derived-graph-refresh-after-structural-edits) permits a complete rebuild only if the full ordinary edit meets the provisional 100 ms benchmark target. Exact C# classes, graph algorithms, serializer code, and measured performance are implementation work.
3. Preserve later unresolved design points—such as incompatible module-family membership, default inout layout, zero-port footprint, harness mapping details, and nested re-expansion—until those features. [Open decisions](docs/open-decisions-and-cautions.md)
